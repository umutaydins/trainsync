## Goal
Every evening the bot asks for a short daily report; answering takes under a minute with buttons
and short replies, and the result is stored in the app (workout + sets, or the reason it didn't
happen) and visible on the web. Works without an Anthropic API key.

## Context
- Bot uses plain httpx long polling (ADR 0013). Inline keyboards need `callback_query` handling
  and `answerCallbackQuery`; add both to the client.
- Training API (P6.2) with idempotent `PUT` by client id; message packs for tone (if present).

## Scope
1. Data: migration + model `daily_checkins` (`date` unique, `status` done/partial/skipped/rest/
   sick_or_injured, `workout_id` nullable, `reason_note`, `sleep_hours` nullable, `energy_1_5`
   nullable, `body_weight_kg` nullable → also written to `body_metrics`, `created_at`, `updated_at`).
   `/v1/checkins`: get by date, list range, idempotent `PUT /v1/checkins/{date}`; streak and
   adherence summary (`planned days done / planned days`, current and longest streak).
2. Scheduler: worker cron at `CHECKIN_TIME` (default `21:00`, timezone `CHECKIN_TZ`
   default `Europe/Istanbul`) sends the prompt to the allowlisted chat **only if no check-in
   exists for today**; `CHECKIN_REMINDER_MINUTES` (default 90) sends one reminder, then stops.
   Also on demand: `/report` or the plain words "rapor"/"report".
3. Conversation (finite-state machine, state in Redis with 6 h TTL, keyed by chat + date):
   - Q1 with inline buttons: ✅ Done · 🟡 Partly · ❌ Skipped · 😴 Rest day · 🤕 Sick/injured.
   - Done/Partly + an active program day → walk the planned exercises one by one, showing
     plan and suggested weight; buttons **"As planned"**, **"+2.5 kg"**, **"−2.5 kg"**,
     **"Skip exercise"**, or type `80x5x3` / `80x5,5,4` / `bw x12x3`; the bot echoes what it
     stored and moves on. No program → ask "what did you do?" and accept the same `/log` syntax
     line by line, `done` to finish.
   - Then optional quick questions with skip buttons: body weight, sleep hours, energy 1–5.
   - Skipped → ask for a short reason (free text, optional). Rest/sick → no pushing, just store.
   - Final message: summary of what was saved (volume, PRs, streak) + "edit" button that reopens
     the flow for today.
   - Every write uses deterministic client ids (`checkin:{date}:{exercise}:{set}`) so Telegram
     retries or double taps never duplicate; stale buttons from old messages are rejected politely.
4. Tone: Skipped with no reason → hardcore pack may push (training only); Rest and Sick/injured
   are always respectful in every tone; body weight never commented on, food only by the savage
   coach's roast of a choice (P6.13, ADR 0032).
5. Web: `/training/checkins` calendar heatmap (status colours), streak and adherence tiles on the
   dashboard, a day view to edit a check-in.

## Acceptance criteria
- [ ] FSM unit tests: every path (done with program, done without program, partly, skipped with/without reason, rest, sick), invalid input re-prompts, "As planned"/±2.5 kg produce the right sets.
- [ ] Scheduler: prompt sent once at the configured local time, not sent when today's check-in exists, one reminder max (tests with injected clock, DST-safe).
- [ ] Duplicate callback/message delivery → no duplicate sets or check-ins (integration with fake Telegram).
- [ ] Streak/adherence match a hand-computed fixture; web heatmap renders it (component test).
