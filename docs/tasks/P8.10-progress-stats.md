## Goal
Every user sees how their training, eating and body weight change over a period, compared with
the period before, in their own time zone.

## Context
ADR 0038 (aggregation in SQL per local day, the period rules, the trigger-versioned Redis
cache). Builds on the per-user tables of P8.2 and the training math of P6.3 (ADR 0018).

## Scope
1. Periods: `week`, `last_week`, `month`, `last_month`, `3m`, `6m`, `year`, `12m`, `all` and
   `custom` (`from`/`to`), resolved to inclusive local days in the user's time zone. Each period
   but `all` has a previous period of the same length; every number carries the change against
   it (absolute and %).
2. `GET /v1/stats/summary?period=…`: the existing totals / per sport type / longest activity
   (unchanged fields), plus
   - endurance per sport group (run, ride, walk, swim, other): distance, moving time,
     elevation, count, average speed, time-weighted average heart rate, longest and fastest;
   - strength: sessions, working sets, reps, tonnage, volume per muscle and per exercise, best
     e1RM per lift (Epley, sets of at most 10 reps), PR count, program adherence (planned vs
     done sessions and sets of the active program);
   - consistency: active days, current and longest training streak (weeks) and check-in streak
     (days), check-in completion rate;
   - nutrition: average daily kcal vs target, protein / carbs / fat averages, days over the
     sugar limit, logging consistency;
   - body: weight first/last/change, 7-day moving average, rate per week; `body_fat_pct` is a
     null slot for Phase 9.
3. `GET /v1/stats/series?metric=…&period=…&bucket=day|week|month`: one zero-filled point per
   bucket (weight: the mean, null when nothing was logged; kcal: with the target). Default
   bucket: day up to 31 days, week up to 183 days, month beyond.
4. `GET /v1/stats/heatmap?year=…`: one value per local day of the year (training minutes and
   sessions, the check-in status).
5. `GET /v1/stats/prs?period=…`: e1RM records in order, with the value they beat.
6. Redis cache for windows of `STATS_CACHE_MIN_DAYS` or more, keyed by the user's data version;
   a trigger bumps the version on every write to the user's tables.
7. Index `workout_sets (user_id, completed_at)`; the IDOR suite covers every stats endpoint.

## Acceptance criteria
- [ ] Period boundaries are local midnights, also across a DST change (tests in two zones).
- [ ] The previous period has the same length (a calendar unit: the unit before); an empty period
      gives zeros and null changes.
- [ ] e1RM ignores sets above 10 reps and warm-ups; a PR is a strictly higher e1RM than every
      earlier set of the lift; streaks and the heatmap match hand-computed fixtures.
- [ ] A write to any of the user's tables changes the cache key; another user's write does not.
- [ ] With three years of seeded data the summary answers in under 300 ms locally (test).
