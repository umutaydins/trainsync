## Goal
A typed, authenticated read endpoint over the stored activities that pages efficiently.

## Context
- `docs/architecture.md` → §7 Read API.

## Scope
1. `src/trainsync/core/deps.py` — `require_api_key` dependency: `X-API-Key` compared in constant
   time against every configured key; `401` with `WWW-Authenticate: ApiKey` otherwise. Applied to
   all `/v1` routes.
2. `GET /v1/activities?from=&to=&sport_type=&limit=50&cursor=` (`limit` 1–200):
   - ordered by `start_date DESC, id DESC`, excludes soft-deleted rows;
   - opaque cursor = urlsafe-base64 JSON `{"start_date": iso, "id": int}`; next page uses
     `(start_date, id) < (:start_date, :id)` (row-value comparison, hits the index);
   - response `{"items":[Activity], "next_cursor": str | null, "last_synced_at": datetime | null}`.
   - invalid cursor → `400`.
3. Response schema `Activity` (no `raw` by default; `?include=raw` optional).
4. Which athlete? Single-user service: all active athletes; add optional `athlete_id` filter.
5. ADR (next free number): "Keyset pagination over offset".

## Acceptance criteria
- [ ] Paging through 1,000 activities with `limit=200` returns every activity exactly once in order, even when new activities are inserted between page requests (test).
- [ ] Filters (`from`, `to`, `sport_type`) combine correctly (parametrized test).
- [ ] Missing/wrong API key → 401; valid → 200 (test).
- [ ] `EXPLAIN` of the page query uses the `(athlete_id, start_date desc)` index (integration test asserting on plan text, data volume large enough).
