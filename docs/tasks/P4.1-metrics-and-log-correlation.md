## Goal
Every important behaviour (Strava calls, retries, breaker, budget, jobs, webhooks, HTTP latency) is
measurable at `/metrics`, and every log line can be tied to a request or job.

## Context
- `docs/phases/phase-4-reliability-ci.md` → task 1 (metric names are fixed there — use them exactly).

## Scope
1. `src/trainsync/core/metrics.py` — define the metrics from the phase doc:
   `strava_requests_total{endpoint,status}`, `strava_request_duration_seconds{endpoint}`,
   `strava_retries_total`, `strava_circuit_state` (0 closed, 1 half_open, 2 open),
   `strava_ratelimit_usage_ratio{window}` (`short`/`daily`), `sync_jobs_total{kind,status}`,
   `webhook_events_total{aspect,status}`, `http_request_duration_seconds{route}` (route template,
   never raw path). Low cardinality only.
2. Instrument client, breaker, budget, jobs, webhook handler/job, HTTP middleware.
3. `GET /metrics` on the API. The worker exposes metrics on its own port
   (`prometheus_client.start_http_server`, `WORKER_METRICS_PORT`, default 9100) — API and worker
   are separate processes; document why multiprocess mode isn't used.
4. Bind `job_id`, `job_name`, `athlete_id` into structlog contextvars for every arq job.

## Acceptance criteria
- [ ] After a fake backfill, `/metrics` (worker) shows non-zero `strava_requests_total` and `sync_jobs_total{kind="backfill",status="succeeded"}` (test).
- [ ] Breaker opening changes `strava_circuit_state` to 2 (test).
- [ ] `http_request_duration_seconds` uses route templates like `/v1/activities` (test).
- [ ] Log lines emitted inside a job include `job_id` (test with captured structlog output).
