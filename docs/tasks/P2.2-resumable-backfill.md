## Goal
`backfill(athlete_id)` pulls the athlete's full history, survives crashes and resumes exactly
where it stopped, and running it twice changes nothing.

## Context
- `docs/architecture.md` → §4 Backfill, `sync_runs` table.
- Page-number pagination shifts when new activities arrive mid-backfill. Use a **time cursor**:
  always request `page=1&per_page=200&before=<cursor>` where `cursor` is the oldest `start_date`
  seen so far (unix seconds). An empty page means done.

## Scope
1. `src/trainsync/sync/backfill.py` — job function `backfill(ctx, athlete_id)`:
   - find a `sync_runs` row with `kind=backfill` and status `running|paused` for the athlete, or
     create one (`cursor={"before": null}`);
   - loop: fetch page with `before=cursor` → in **one transaction**: upsert the page and update
     `sync_runs.cursor`, `pages`, `upserted` → next cursor = min `start_date` of the page;
   - on empty page: `status=succeeded`, `finished_at=now`;
   - on `StravaAuthError`: `status=failed`, `error` set, stop (no retry storm);
   - on unexpected error: `status=failed` with a short error string, re-raise (arq records it).
   - activities with identical `start_date` at a page boundary must not be skipped: use
     `before = min_start_date + 1` and rely on idempotent upserts (document this choice).
2. Only one backfill per athlete at a time: arq job id `backfill:{athlete_id}`, plus a check
   against an already `running` `sync_runs` row updated in the last N minutes.
3. Hooks for P2.4/P2.5: the job asks a `budget.allow(priority="low")` callable before each page
   (a permissive stub for now) and handles `RateLimited` by marking the run `paused` and
   re-enqueueing itself with `_defer_until=reset_at`.
4. Register the job in `WorkerSettings`.

## Out of scope
Real budget logic (P2.4), circuit breaker (P2.5).

## Acceptance criteria
- [ ] Backfill of 1,000 fake activities (fake_strava seed) stores 1,000 rows and a `succeeded` run (integration test).
- [ ] Running backfill again upserts 0 rows (test).
- [ ] **Crash/resume:** cancel the job after the 3rd page (e.g. fault injection in fake_strava or cancelling the task), run again → it continues from the stored cursor; total pages fetched across both runs = pages needed + at most 1 (assert via `/_control/stats`) (integration test).
- [ ] Activities sharing a `start_date` across a page boundary are all stored (test with crafted seed).
- [ ] `RateLimited` → run `paused`, job re-enqueued with defer ≈ reset time (unit test with stubs).
