## Goal
Background work backs off before Strava's limits are hit, high-priority (webhook-driven) work keeps
flowing, and a 429 leads to waiting for the window reset instead of a retry storm.

## Context
- `docs/architecture.md` → §3 Rate limits.
- `RateLimitSnapshot`, `next_window_reset` (P1.5); `budget.allow` hook and `RateLimited`
  handling in backfill (P2.2).

## Scope
1. `src/trainsync/strava/budget.py` — `RateBudget(redis, clock, low_priority_threshold=0.8)`:
   - `record(snapshot)` — the client's `on_rate_limit` callback; stores the latest usage/limits in
     a Redis hash `ratelimit:latest` with the window it belongs to, TTL until the daily reset.
   - `allow(priority) -> Allowance` — `high` always allowed unless the 15-min window is exhausted;
     `low` denied when `short_ratio >= 0.8` or `daily_ratio >= 0.8`, returning `resume_at`
     (next 15-min boundary or next daily reset).
   - Snapshot from a previous window is ignored (usage resets on the quarter hour).
   - `blocked_until` key set after a 429; both priorities wait until it passes.
2. Wire into `StravaClient` (record) and into backfill/incremental (`allow("low")`), and expose a
   `priority` argument on client methods so P3.3 can pass `high`.
3. ADR (next free number): "Two-priority rate budget" — why fresh webhook data beats backfill
   progress, why 80%, why read headers instead of hard-coded limits.

## Out of scope
Circuit breaker (P2.5).

## Acceptance criteria
- [ ] Unit tests for `allow`: below/above threshold, stale snapshot from previous window, daily exhaustion, after a 429.
- [ ] With fake_strava `RATE_LIMIT_15MIN=50`, a 1,000-activity backfill pauses before getting a 429, resumes after the (injected/advanced) window boundary and completes; fake_strava stats show **no more than 1** 429 response (integration test).
- [ ] While backfill is paused, a `high` priority `get_activity` call still succeeds (test).
