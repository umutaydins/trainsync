## Goal
People with an invite can create an account and sign in; sessions are revocable and abuse-limited.

## Context
ADR 0034. Until now one API key and one dashboard password guarded everything.

## Scope
1. `modules/users` (users, user_settings) and `modules/auth` (sessions, invites, resets, limits):
   migration 0015 (users, sessions, invites, password_resets, user_settings).
2. argon2id hashing (argon2-cffi), password policy 10–128 characters.
3. `POST /v1/auth/register` (invite code unless `REGISTRATION_MODE=open`; `closed` refuses),
   `POST /v1/auth/login` → `{token, expires_at, user}`, `POST /v1/auth/logout`, `GET /v1/me`,
   `PATCH /v1/me`, `POST /v1/me/password` (revokes the other sessions), `GET /v1/me/sessions`,
   `DELETE /v1/me/sessions/{id}`, `POST /v1/auth/reset` (token + new password).
4. Opaque tokens: 32 random bytes, SHA-256 stored, sliding `SESSION_TTL_DAYS`, cap
   `SESSION_MAX_AGE_DAYS`, touch at most every `SESSION_TOUCH_INTERVAL_S`.
5. Limits (Redis, injected clock): per-email lockout, per-address login and register limits.
6. Owner-only API: `POST/GET /v1/admin/invites`, `DELETE /v1/admin/invites/{id}`,
   `GET /v1/admin/users` (no data access), `POST /v1/admin/users/{id}/reset-link`.
7. CLIs: `scripts/invite.py create|list|revoke`, `scripts/owner.py set-password|reset-link`.
8. `CurrentUser` dependency: Bearer session, or API key (owner, or `X-Acting-User` from a
   service key, ADR 0036).

## Out of scope
Email delivery, 2FA, social login.

## Acceptance criteria
- [ ] Register in each mode; invites single-use and expiring; duplicate email refused.
- [ ] Login returns a token whose hash is stored; logout, revoke and password change revoke.
- [ ] Expired, revoked and unknown tokens get 401; expiry slides and stops at the cap.
- [ ] Lockout after `LOGIN_MAX_FAILURES` per email, per-address limits on login and register.
- [ ] Reset link is single-use, expires, and revokes every session.
- [ ] Owner-only endpoints answer 403 to a user.

## Verify
`make verify`
